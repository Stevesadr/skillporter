# Supported agents

> Generated from `agents/*.yaml` by `scripts/generate-agent-matrix.mjs`.
> Do not edit this file by hand: edit the profile and regenerate.

6 capability profiles. A profile is data, not code: adding an agent means adding one
YAML file and citing a source for every fact in it. No command in the tool names an agent.

`verified` means every fact traces to a primary source retrieved on the date shown. `partial` means some
facts are documented and at least one is not. `unverified` means the profile exists but nothing in it was
confirmed. An unknown fact is never guessed: it is written as `unknown` and reported as a warning.

## Profile notes

- **Claude.ai / Skills API upload** — The upload surface: the claude.ai skill upload and the Skills API (/v1/skills). It is not a filesystem target. You hand over a bundle — a zip, a set of files, or a directory through the SDK helper — and it is expanded to /skills/{name}/ inside a code-execution container.
Official documentation is explicit about exactly two frontmatter fields, `name` and `description`, and about their constraints. No official page says what happens to a third field: it is not documented as accepted and not documented as rejected. That is the gap this profile records. `name` and `description` are emitted; every other field is dropped and reported, because emitting it would be a guess about a validation rule nobody has published. `verification: partial` is therefore deliberate and specific: the field list and the name/description rules are verified, the treatment of any other field is not.
Custom Skills do not sync between surfaces, so this is a separate target from claude-code rather than an option on it.
- **Claude Code** — Claude Code implements the Agent Skills spec and extends it heavily. Two distinct surfaces exist and they are NOT the same target: (a) local Claude Code skill directories, which accept every field below, and (b) uploading a skill to claude.ai / the Skills API / package_skill.py, which accepts ONLY name, description, license, compatibility, metadata and allowed-tools and hard-errors on any other key. This profile describes (a). Emitting for (b) must be modelled as a separate target.
- **Codex CLI** — Codex reads skills from a shared `.agents/skills` root, not from a `.codex/skills` directory. The same root is read by DeepSeek Harness and OpenCode, which makes `.agents/skills` the de facto interop point between agents and the natural default output target. Optional presentation and policy metadata lives in a sidecar `agents/openai.yaml` inside the skill directory, not in SKILL.md frontmatter.
- **DeepSeek Harness (dsh)** — dsh reads the Agent Skills format natively and needs no manifest. It is in developer preview and its README promises compatibility-breaking changes; filesystem discovery is the most stable part. The old `.dsh-plugin` repository plugin path was removed on 2026-08-09 with no compatibility parser, so any tutorial describing `.dsh-plugin/plugin.json` is obsolete. Facts below were confirmed against the repository source, not only the documentation, because the generated config catalog is incomplete for the skill packages.
- **Kimi Code CLI** — Kimi Code CLI (Moonshot AI, npm @moonshot-ai/kimi-code) reads an Agent Skills-like format with its own frontmatter dialect: camelCase field names that also accept kebab-case and snake_case aliases. It is the only surveyed agent with a `type` field and a `flow` skill type. Two forms are accepted: a directory with SKILL.md (name and description mandatory) and a flat .md file at the skills root (both optional, with fallbacks). Verified against the Chinese-language official documentation at kimi.com/code/docs; the CLI itself is TypeScript on Node 22.19+. FORMER DOCUMENTATION CONFLICT, NOW CLOSED: a help-centre article once said name and description were optional with a directory-name fallback, and that flow skills run as /flow:<name>. That article has been withdrawn and its successor defers to the reference documentation on every CLI skill question, so the disagreement no longer exists and the reference reading stands unchallenged. See docs/research.md section 8.9. The emitter must always write name and description for this target, and must never generate a /flow: command.
- **OpenCode** — OpenCode has the most unusual model of the five surveyed agents: the skill identifier comes from the file path, not from frontmatter, and frontmatter `name` is only a display label. It is also the only agent here that reads another agent's directory natively (.claude/skills) as a first-class compatibility source. Discovery is deeper than the others (six levels) and it silently accepts flat Markdown files at the source root.
